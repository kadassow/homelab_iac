# Authentik OIDC Setup — Notes & Troubleshooting Log

Documents the Authentik deployment and the first working OIDC integration
(NutriTrace). Meant to sit alongside `PROXMOX_GPU_SETUP.md` and
`KOPIA_BACKUP_STRATEGY.md` at the repo root — same reasoning: capture the
non-obvious gotchas so they don't have to be re-derived from source code
again next time.

## Deployment

- Authentik runs in its own dedicated LXC, provisioned via the Proxmox
  community helper scripts (not Ansible-managed — same treatment as other
  host-level/out-of-band infra, consistent with `PROXMOX_GPU_SETUP.md`).
- LXC IP: `192.168.69.157`, admin UI at `https://authentik.sparkylab.win/`
  (also reachable directly at `192.168.69.157:9443`).
- NPM already has a proxy host routing the domain to the LXC.
- Isolation rationale: dedicated LXC rather than joining `vm2-services`'
  compose stacks — matches the same security-boundary pattern used for the
  Kopia server (see `KOPIA_BACKUP_STRATEGY.md`).
- **Known open item**: there's a recent Authentik CVE (2026-40166) where
  non-admin users with an OAuth2 access token could retrieve client secrets
  for confidential providers they'd authenticated against — fixed in
  2025.12.5 and 2026.2.3. Worth confirming the deployed version is patched,
  especially since this instance is internet-facing.

## Two integration patterns going forward

- **Native OIDC support** (NutriTrace today) → standard OAuth2/OIDC
  Provider + Application in Authentik.
- **No native OIDC support** (arr stack, Stash, etc.) → will need
  **Forward Auth (Proxy Provider)** instead — not yet built, see Open
  Questions below.

## NutriTrace OIDC — working configuration

### Authentik side

- Application slug: `nutritrace` (must match exactly — NutriTrace's issuer
  URL is hardcoded to `.../application/o/nutritrace/`)
- Provider type: OAuth2/OIDC, Client type: Confidential
- Client ID manually set to `nutritrace` (Authentik's autogenerated default
  doesn't match what the compose file expects)
- Scopes: `openid profile email`
- **Redirect URIs/Origins**: `https://nutritrace.sparkylab.win/api/auth/oidc/callback/1`
  — must match NutriTrace's own redirect URI **exactly**, including the
  trailing `/1` provider-ID suffix (see below)

### NutriTrace side (env vars)

NutriTrace's OIDC bootstrap (`server/lib/oidc-env.js`) reads a numbered
`OIDC_PROVIDER_N_*` convention, with unnumbered `OIDC_*` as an alias for
provider 1:

```
OIDC_ISSUER=https://authentik.sparkylab.win/application/o/nutritrace/
OIDC_CLIENT_ID=nutritrace
OIDC_CLIENT_SECRET=<from vault_nutritrace_oidc_client_secret>
OIDC_REDIRECT_URIS=https://nutritrace.sparkylab.win/api/auth/oidc/callback/1
```

**`OIDC_REDIRECT_URIS` is not documented in NutriTrace's top-level README**
env var table — only discoverable by reading `oidc-env.js` directly inside
the container. Comma-separated if multiple values are ever needed.

Vault/all.yml vars in use:
- `NUTRITRACE_JWT_SECRET` — internal session-token signing, unrelated to
  OIDC entirely (NutriTrace signs its own login sessions with this
  regardless of auth method).
- `NUTRITRACE_OIDC_ISSUER`, `_CLIENT_ID`, `_CLIENT_SECRET` — the actual
  OAuth2 client credentials presented to Authentik.
- `NUTRITRACE_OIDC_REDIRECT_URIS` — **added this session**, needs to be
  confirmed present in both `group_vars/all.yml` and
  `mediastack/docker-compose.yml`'s `nutritrace` service environment block.

## Troubleshooting chain from this session (in order encountered)

Each of these presented as the SSO button either erroring immediately or
failing partway through — worth reading in order since later errors only
appeared after earlier ones were fixed:

1. **"Provider has no redirect_uris configured" (immediate 500, never left
   NutriTrace's domain)** — NutriTrace's own `redirect_uris` DB field was
   empty. This field is populated *only* via `OIDC_REDIRECT_URIS` at boot
   or the admin UI — it is **not** derived automatically from the request,
   and is **not** part of the basic `OIDC_ISSUER`/`CLIENT_ID`/`CLIENT_SECRET`
   trio. Fixed by adding `OIDC_REDIRECT_URIS` (see above).

2. **"Discovery Failed — only valid absolute URLs can be requested"** —
   `vault_oidc_issuer` was missing the `https://` scheme, so
   `NUTRITRACE_OIDC_ISSUER` resolved to a schemeless string. Fixed by
   ensuring `vault_oidc_issuer: "https://authentik.sparkylab.win"` (no
   trailing slash — `all.yml` already appends
   `/application/o/nutritrace/`).

3. **Redirect_uris error came back after the issuer fix** — changing the
   issuer string changed the `(issuer_url, client_id)` natural key that
   `oidc-env.js` uses to match existing DB rows on boot, so a **new**
   provider row got inserted (not an update) at a different ID than the
   `/callback/1` URL already configured everywhere assumed. Since this
   instance had no real data yet, resolved by deleting the SQLite DB file
   and letting a clean boot re-seed provider ID `1` from scratch — much
   simpler than hunting down the mismatched ID once there's nothing to
   lose. **Once real data exists, this DB-wipe shortcut is no longer safe**
   — would need to inspect `oidc_providers` table directly (no `sqlite3`
   binary in the container; query via `docker exec nutritrace node
   --input-type=module -e "..."` against `/app/server/db.js`, or hit the
   admin API's `/providers` endpoint from the browser Network tab instead).

4. **"No account linked to this identity"** — expected given
   `OIDC_AUTO_REGISTER=0` (deliberately set to avoid blanket
   auto-onboarding — see original compose comment). A successful Authentik
   login does not by itself create or match a NutriTrace account. Fix:
   log in locally first, then visit
   `https://nutritrace.sparkylab.win/api/auth/oidc/login/1?link=1` while
   that local session is active — this is NutriTrace's account-linking
   flow (`req.query.link === '1' && !!req.user'` in `routes/oidc.js`).
   After linking once, the plain "Sign in with Authentik" button resolves
   correctly to the linked account.

**Net result: OIDC login for NutriTrace is confirmed working end-to-end**
as of this session.

  same upstream codebase pattern likely applies.

# Authentik LXC vs VM-services deploy
Keep it as its own LXC — this is actually the same reasoning you already applied to the Kopia server, and it applies even more strongly to Authentik.

Why not vm2-services:

vm2-services is, by a wide margin, the highest-risk-footprint host in your homelab — it runs qBittorrent pulling from arbitrary torrent peers, Stash, and a stack of arr apps that have a track record of CVEs. If any one of those gets popped, the blast radius today is "that app, on that VM." If Authentik lived in the same docker-compose stack on that VM, a compromise there would also hand over your identity provider — session-signing keys, every OAuth2 client secret (NutriTrace's, and eventually Stash's and the arr stack's forward-auth config), and the ability to forge valid logins for anything gated behind it. That turns "one app got popped" into "everything Authentik protects is now also compromised" — worse than the sum of its parts, not just an additional risk.

This is exactly the same logic your KOPIA_BACKUP_STRATEGY.md already lays out for why the Kopia server got its own dedicated LXC instead of living on vm2-services: the thing holding the keys shouldn't share a blast radius with the thing most likely to get hit.

The one real downside: the Authentik LXC currently sits outside your Ansible-managed inventory (same as Kopia was, before you onboarded it). That's a legitimate gap, but it's independently fixable — you already said you want to bring your other LXCs into Ansible generically later. That's a reproducibility problem to solve on its own timeline, not a reason to fold Authentik into vm2-services's docker compose stack.

Net: dedicated LXC stays the right call.
